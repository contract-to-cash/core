## A. アーキテクチャ・設計決定

### 良い点

1. **DDD/DIPの適用が明確** — ドメイン層、アプリケーション層、インフラ層が適切に分離され、Mermaid図で依存方向を明示
2. **ADRが充実** — CQRS方式、マルチテナント、タイムゾーン等の代替案比較テーブルが網羅的
3. **ビジネスロジックの柔軟性** — 日割り計算3パターン、一時停止3パターン、Projection同期/非同期選択など利用者の選択肢が豊富
4. **冪等性対策** — IdempotencyKey必須化、TTL設定可能
5. **バッチ処理のスケジューラ分離** — OSSはインターフェースのみ提供、環境依存を排除

### 改善が必要な点

1. **「簡易CQRS」の定義が曖昧** — 同期Projection更新時の一貫性保証、非同期更新時のSLA、Projection更新失敗時のリトライ戦略が未定義
2. **マルチテナント対応の責任範囲が不明確** — 「サービス側に委ねる」としながらOSS側の最低限の安全性要件が未定義
3. **セキュリティドキュメントの欠落** — Event Storeアクセス制御、監査ログ改竄対策、プラグインサンドボックス化、PII暗号化戦略がすべて未記載
4. **HA/DR設計の欠落** — Event Store冗長化、バックアップ/RPO/RTO、復旧シーケンスが未定義
5. **規制対応の未考慮** — GDPR（忘れられる権利）、PCI DSS、監査ログ保持期間ポリシーが未記載

---

## B. ドメインモデル・イベントソーシング

### 良い点

1. **Money値オブジェクト** — `big.Rat`で精密な金銭計算、通貨混在防止の型安全設計
2. **集約境界が適切** — Contract/Invoice/PaymentがID参照で分離
3. **イベント構造の充実** — OccurredAt/RecordedAt分離、CorrelationID/CausationIDで分散トレーシング対応
4. **スナップショット戦略** — 100イベントごとのデフォルト、時間/オンデマンド選択可能
5. **楽観的ロック** — expectedVersionで並行更新を制御

### 改善が必要な点

1. **Contract集約の責任肥大化** — ライフサイクル管理・料金設定・トライアル・一時停止がすべて1集約に集中。`ContractTerms`/`TrialManagement`/`SuspensionManagement`への分離を検討
2. **イベント競合の解決戦略が欠落** — 並行操作で同一集約に複数イベントが発行された場合の優先ルールが未定義
3. **Upcaster実装例がない** — SchemaVersion定義のみで、実際のスキーマ移行手順が不明
4. **時刻境界問題** — 月次請求サイクルの端数処理（1/31開始→2月は？）が未考慮
5. **金額精度ルール** — 通貨ごとの小数点以下桁数（JPY=0, USD=2, BTC=8）が未定義
6. **UsageRecordの冪等性詳細** — idempotencyKeyはあるが重複時の処理（更新 vs 無視）が未定義
7. **Projection位置管理** — 再起動後の`fromPosition`管理メカニズムが不明確（`last_processed_position`の永続化が必要）

## C. プラグインシステム・決済ゲートウェイ

### 良い点

1. **フック設計の明確さ** — InvoiceCalculation/ContractLifecycle/Payment/Metrics/InvoiceGenerationが関心ごとに分離
2. **決済フローの網羅性** — Charge/Authorize+Capture/Void/Refund/Cancel＋PaymentMethod管理
3. **エラー型の構造化** — GatewayError + ErrorCode列挙 + Retryableフラグ
4. **複数ゲートウェイルーティング** — GatewayRouterで条件ベースルーティング＋フォールバック
5. **メトリクスKPIの網羅性** — MRR/ARR/Churn/Cohort分析用の定義が包括的
6. **適格請求書対応** — 電子帳簿保存法対応（RegistrationNumber, TaxSummary, SHA-256ハッシュ）

### 改善が必要な点（重要度順）

#### 致命的

1. **PCI DSS違反: `CardSource`型でカード番号・CVCの直接受信**
   - `PaymentSource.Card.Number`（フルカード番号）と`CVC`をサーバーが直接受け取る設計
   - **必須対応**: CardSource型を削除しトークン化フローを強制。クライアント側でStripe.js等のトークナイザーを必須化

#### 高優先

2. **Webhook処理の脆弱性** — タイムスタンプ検証なし（リプレイ攻撃リスク）、イベント重複検出なし、失敗時の再試行メカニズムなし
3. **リトライ機構の欠落** — GatewayErrorのRetryableフラグのみで、指数バックオフ・リトライ上限の標準実装がない
4. **プラグインエラーハンドリング不足** — fail-fast vs best-effort未定義、プラグイン間依存関係の検証メカニズムなし
5. **複数割引プラグインの合算制御なし** — 割引合計が小計を超過するケースの防止ロジックがない

#### 中優先

6. **返金処理の制限なし** — 累計返金額が取引金額を超えないバリデーションがない
7. **トランザクション状態遷移ルール未定義** — Captured→Authorizedなどの無効遷移を防止するロジックがない
8. **バッチ処理の信頼性** — 部分失敗時のリカバリ、冪等性保証（同日複数回実行でデータ重複しない）が未定義
9. **メトリクス間の一貫性** — 複数メトリクス更新を1トランザクションで実行する保証がない

---

## D. 改善計画（5つの改善項目）

### 良い点

1. **問題特定の正確性** — 5つの改善すべてが既存設計の実問題を正しく識別
2. **実装順序の妥当性** — 依存関係に基づく順序（4→5→1→3→2）は論理的
3. **改善2のフック分離** — 会計基準（割引→小計→税）をコード構造で強制する設計は優秀
4. **改善3の型付きイベント** — exhaustive lintでイベント追加漏れを検出可能にする設計
5. **改善5のErrorCode** — API層のHTTPステータスマッピングが明確に実現可能

### 改善が必要な点

1. **プラグインAPI互換性戦略の欠如** — 改善2で破壊的変更が発生するが、semantic versioning（v2.0.0）の宣言や移行ツールの提供計画がない
2. **マイグレーション手順の欠如** — 改善3で文字列イベント→型付きイベントへの移行時、既存EventStoreデータの互換性保証方法が未記載
3. **利用ガイドとの齟齬** — 利用ガイドが現状のAPI（`BeforeCalculation`等）を使用しており、改善2後の新API（`InvoiceLifecycleHook`）との不整合
4. **Engine削除の移行先詳細** — 改善4で「Engineは削除」と明記するが、`SubscriptionEngine`ロジックの具体的な移行先が曖昧
5. **改善計画が見落としている構造的問題**:
   - マルチテナントID戦略（AccountIDスキーム）
   - スナップショットと型付きイベントの同期方法
   - Projection位置管理メカニズム

## E. 横断的な指摘事項

### セキュリティ（全体）

| 項目 | 現状 | 推奨対応 |
|------|------|---------|
| PCI DSS | CardSource直接受信 | **即座に修正**: トークン化フロー強制 |
| 監査ログ改竄対策 | なし | デジタル署名またはMerkleツリー |
| プラグインサンドボックス | なし | 権限管理・危険API制限の定義 |
| PII暗号化 | なし | AES-256-GCMでのアットレスト暗号化 |
| Webhook | 署名検証のみ | +タイムスタンプ検証+重複検出 |

### エッジケース（全体）

| 項目 | 現状 | 推奨対応 |
|------|------|---------|
| 月末境界 | 未考慮 | MonthlyBillingCycleBehavior定義 |
| 通貨精度 | 未定義 | Currency別Scaleルール |
| ゼロ金額 | 曖昧 | 無料トライアル・ゼロ請求書の明示 |
| 過払い | 未定義 | 返金 or クレジット化のルール |
| タイムゾーン | UTC固定 | 請求日判定のTZ基準を明示 |

## 推奨アクション（優先順位）

### P0: 実装前に必須

1. **PCI DSS対応** — `CardSource`型を削除、トークン化フローの強制
2. **Webhook堅牢性強化** — タイムスタンプ検証、重複検出、DeadLetterQueue
3. **プラグインAPI互換性戦略** — semantic versioning、v1.x LTS、移行ツール

### P1: 改善計画への追記

4. **マイグレーション手順のADR化** — 文字列→型付きイベント移行ステップ
5. **セキュリティアーキテクチャドキュメント** — アクセス制御、暗号化、PII管理
6. **金額精度ルール** — 通貨ごとの小数点以下桁数定義
7. **Engine削除の移行先詳細** — SubscriptionEngineロジックの具体的分割

### P2: 設計の深化

8. **CQRS整合性ガイド** — Projection更新の一貫性保証方針
9. **イベント競合解決戦略** — 並行操作の優先ルール定義
10. **Contract集約の責任分離** — ContractTerms/TrialManagement等への分割検討
11. **マルチテナントID戦略** — AccountIDスキームの明示

### P3: 運用準備

12. **HA/DR設計** — Event Store冗長化、RPO/RTO
13. **パフォーマンスSLA** — イベント再生速度・クエリ応答時間目標
14. **運用手順書** — スキーマ変更手順、トラブルシューティング
