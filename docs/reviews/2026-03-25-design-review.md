## A. アーキテクチャ・設計決定

### 良い点

1. **DDD/DIPの適用が明確** — ドメイン層、アプリケーション層、インフラ層が適切に分離され、Mermaid図で依存方向を明示
2. **ADRが充実** — CQRS方式、マルチテナント、タイムゾーン等の代替案比較テーブルが網羅的
3. **ビジネスロジックの柔軟性** — 日割り計算3パターン、一時停止3パターン、Projection同期/非同期選択など利用者の選択肢が豊富
4. **冪等性対策** — IdempotencyKey必須化、TTL設定可能
5. **バッチ処理のスケジューラ分離** — OSSはインターフェースのみ提供、環境依存を排除

### 改善が必要な点

1. **「簡易CQRS」の定義が曖昧** — 同期Projection更新時の一貫性保証、非同期更新時のSLA、Projection更新失敗時のリトライ戦略が未定義
2. **マルチテナント対応の責任範囲が不明確** — 「サービス側に委ねる」としながらOSS側の最低限の安全性要件が未定義
3. **セキュリティドキュメントの欠落** — Event Storeアクセス制御、監査ログ改竄対策、プラグインサンドボックス化、PII暗号化戦略がすべて未記載
4. **HA/DR設計の欠落** — Event Store冗長化、バックアップ/RPO/RTO、復旧シーケンスが未定義
5. **規制対応の未考慮** — GDPR（忘れられる権利）、監査ログ保持期間ポリシーが未記載

## B. ドメインモデル・イベントソーシング

### 良い点

1. **Money値オブジェクト** — `big.Rat`で精密な金銭計算、通貨混在防止の型安全設計
2. **集約境界が適切** — Contract/Invoice/PaymentがID参照で分離
3. **イベント構造の充実** — OccurredAt/RecordedAt分離、CorrelationID/CausationIDで分散トレーシング対応
4. **スナップショット戦略** — 100イベントごとのデフォルト、時間/オンデマンド選択可能
5. **楽観的ロック** — expectedVersionで並行更新を制御

### 改善が必要な点

1. **Contract集約の責任肥大化** — ライフサイクル管理・料金設定・トライアル・一時停止がすべて1集約に集中
2. **イベント競合の解決戦略が欠落** — 並行操作で同一集約に複数イベントが発行された場合の優先ルールが未定義
3. **Upcaster実装例がない** — SchemaVersion定義のみで、実際のスキーマ移行手順が不明
4. **時刻境界問題** — 月次請求サイクルの端数処理（1/31開始→2月は？）が未考慮
5. **金額精度ルール** — 通貨ごとの小数点以下桁数（JPY=0, USD=2, BTC=8）が未定義
6. **UsageRecordの冪等性詳細** — idempotencyKeyはあるが重複時の処理（更新 vs 無視）が未定義
7. **Projection位置管理** — 再起動後の`fromPosition`管理メカニズムが不明確

## C. プラグインシステム・決済ゲートウェイ

### 良い点

1. **フック設計の明確さ** — InvoiceCalculation/ContractLifecycle/Payment/Metrics/InvoiceGenerationが関心ごとに分離
2. **決済フローの網羅性** — Charge/Authorize+Capture/Void/Refund/Cancel＋PaymentMethod管理
3. **エラー型の構造化** — GatewayError + ErrorCode列挙 + Retryableフラグ
4. **複数ゲートウェイルーティング** — GatewayRouterで条件ベースルーティング＋フォールバック
5. **メトリクスKPIの網羅性** — MRR/ARR/Churn/Cohort分析用の定義が包括的
6. **適格請求書対応** — 電子帳簿保存法対応（RegistrationNumber, TaxSummary, SHA-256ハッシュ）
7. **~~PCI DSS対応~~** — ✅ CardSource削除済み、トークン専用の非通過型設計
8. **~~Webhook堅牢性~~** — ✅ 双方向タイムスタンプ検証、重複検出、DLQ、エラー分類
9. **~~API互換性~~** — ✅ SemVer方針、LTS、移行ガイド、非推奨プロセス

### 改善が必要な点（P0対応後の残存課題）

1. **プラグインエラーハンドリング不足** — fail-fast vs best-effort未定義、プラグイン間依存関係の検証メカニズムなし
2. **複数割引プラグインの合算制御なし** — 割引合計が小計を超過するケースの防止ロジックがない
3. **返金処理の制限なし** — 累計返金額が取引金額を超えないバリデーションがない
4. **トランザクション状態遷移ルール未定義** — Captured→Authorizedなどの無効遷移を防止するロジックがない
5. **バッチ処理の信頼性** — 部分失敗時のリカバリ、冪等性保証が未定義
6. **メトリクス間の一貫性** — 複数メトリクス更新を1トランザクションで実行する保証がない

## D. 改善計画（5つの改善項目）

### 良い点

1. **問題特定の正確性** — 5つの改善すべてが既存設計の実問題を正しく識別
2. **実装順序の妥当性** — 依存関係に基づく順序（4→5→1→3→2）は論理的
3. **改善2のフック分離** — 会計基準（割引→小計→税）をコード構造で強制する設計は優秀
4. **改善3の型付きイベント** — exhaustive lintでイベント追加漏れを検出可能にする設計
5. **改善5のErrorCode** — API層のHTTPステータスマッピングが明確に実現可能

### 改善が必要な点

1. **マイグレーション手順の欠如** — 改善3で文字列イベント→型付きイベントへの移行時、既存EventStoreデータの互換性保証方法が未記載
2. **利用ガイドとの齟齬** — 利用ガイドが現状のAPI（`BeforeCalculation`等）を使用しており、改善2後の新API（`InvoiceLifecycleHook`）との不整合
3. **Engine削除の移行先詳細** — 改善4で「Engineは削除」と明記するが、`SubscriptionEngine`ロジックの具体的な移行先が曖昧
4. **改善計画が見落としている構造的問題**:
   - マルチテナントID戦略（AccountIDスキーム）
   - スナップショットと型付きイベントの同期方法
   - Projection位置管理メカニズム
